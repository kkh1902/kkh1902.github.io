## 지시서도 결국 유지보수 대상이다

Claude Code를 오래 쓰다 보면 프로젝트 지시서(CLAUDE.md 같은 파일)가
점점 길어진다. 새 규칙이 생길 때마다 아래에 덧붙이기만 하면, 어느 순간
모델도 사람도 어떤 규칙이 지금도 유효한지 헷갈리기 시작한다. 코드와
마찬가지로, 지시서도 주기적으로 정리하지 않으면 썩는다.

## 내가 쓰는 원칙 3가지

**1. 결론과 이유를 분리한다.**
"이렇게 해라"만 적으면 나중에 예외 상황에서 판단을 못 한다. 결론 뒤에
"왜 그런지"를 한 줄만 붙여두면, 비슷하지만 다른 상황에서도 그 이유를
기준으로 스스로 판단할 수 있다. 예: "A 대신 B를 써라 — 왜냐하면 과거에
A로 인해 X 문제가 있었다."

**2. 배경 서사는 별도 파일로 뺀다.**
"어떻게 이 규칙이 생겼는지"에 대한 긴 경위는 메인 지시서에 남기지 않는다.
결론만 메인에 남기고, 조사 과정이나 시행착오는 히스토리 문서로 분리해
링크만 건다. 메인 지시서는 "지금 지켜야 할 규칙"만 빠르게 훑을 수 있어야
한다.

**3. 날짜를 같이 남긴다.**
규칙이 언제 생겼는지 적어두면, 오래된 규칙과 최근 규칙을 구분하기
쉬워진다. 특히 빠르게 바뀌는 프로젝트에서는 "이 규칙이 아직도 맞는지"를
판단할 때 날짜가 결정적인 단서가 된다.

## 정리

지시서가 길어지는 건 프로젝트가 성장하고 있다는 신호이기도 하다. 다만
그 길이를 그냥 방치하면 오히려 모델의 판단을 흐리게 만든다. 코드 리뷰처럼
지시서도 가끔 통째로 다시 읽고 정리하는 시간이 필요하다.
