## TL;DR

인덱스는 "책의 목차"다. 본문(테이블)을 처음부터 끝까지 넘기지 않고, 목차(B-Tree)를 따라
한 번에 원하는 페이지로 점프한다. 대신 책 내용이 바뀔 때마다 목차도 같이 고쳐야 해서
쓰기(INSERT/UPDATE/DELETE)는 느려진다.

## 비유 한 줄

인덱스 없는 테이블 조회 = 1000페이지 책을 1페이지부터 끝까지 다 읽어서 원하는 단어 찾기
(Full Scan, O(N)). 인덱스 있는 조회 = 목차에서 페이지 번호를 찾아 바로 그 페이지로
펼치기(B-Tree 탐색, O(log N)).

## 개념 표

| 용어 | 비유 | 한줄 설명 |
|---|---|---|
| Full Table Scan | 책을 처음부터 끝까지 읽기 | 인덱스 없이 전체 레코드를 순서대로 검사, O(N) |
| B-Tree | 계층형 목차 | 자식 노드를 여러 개 가질 수 있는 균형 트리, 탐색 O(log N) |
| B+Tree | 목차 + 마지막 페이지끼리 책갈피 연결 | 실제 값은 리프 노드에만 저장하고 리프끼리 연결 리스트로 이어 범위 검색에 유리 |
| 쓰기 비용 | 목차 다시 쓰기 | 레코드가 추가/삭제/수정될 때마다 인덱스 구조도 같이 갱신해야 함 |

## 구조 다이어그램

```
[인덱스 없음]                     [인덱스(B+Tree) 있음]
 레코드 1 → 비교                    루트 노드
 레코드 2 → 비교                   /    |    \
 레코드 3 → 비교               [1-30] [31-60] [61-90]  ← 중간 노드
 ...  (전부 검사, O(N))            ↓      ↓      ↓
 레코드 N → 비교                리프→리프→리프 (연결 리스트, 값 실제 저장)
                                  ↑
                          탐색 경로만 따라가면 끝, O(log N)
```

## 동작 원리 (왜?)

| 질문 | 답 |
|---|---|
| 왜 트리 구조면 빨라지는가? | 매 단계마다 비교 대상 범위를 절반 이하로 줄여나가기 때문. 100만 건이어도 트리 높이는 20 정도라 비교 20번이면 끝남 |
| 왜 B+Tree가 범위 검색(`WHERE age > 20`)에 유리한가? | 리프 노드끼리 연결 리스트로 이어져 있어서, 시작점만 찾으면 그 뒤로는 트리를 다시 안 타고 리프를 옆으로 쭉 읽기만 하면 됨 |
| 왜 쓰기가 느려지는가? | 값이 바뀌면 기존 위치의 항목을 지우고 새 위치에 다시 넣어야 트리의 정렬 상태가 유지됨 — 레코드 하나 바꾸는데 인덱스 구조까지 같이 손봐야 함 |
| 언제 인덱스를 걸면 좋은가? | WHERE·JOIN·ORDER BY에 자주 쓰이는 컬럼, 중복이 적은(선택도가 높은) 컬럼 |
| 언제 피해야 하는가? | 중복 값이 많은 컬럼(성별 등), INSERT/UPDATE가 매우 잦은 컬럼 |

## 예시

```sql
-- 인덱스 없이 100만 건 중 특정 이메일 찾기 → Full Scan
SELECT * FROM users WHERE email = 'kkh1902@naver.com';

-- 인덱스를 걸면 그 다음부터는 B+Tree 탐색으로 처리됨
CREATE INDEX idx_users_email ON users(email);

-- 쿼리 플래너가 인덱스를 쓰는지 확인
EXPLAIN SELECT * FROM users WHERE email = 'kkh1902@naver.com';
```

## 요약 표

| 상황 | 인덱스 없음 | 인덱스 있음 |
|---|---|---|
| 조회 속도 | O(N), 느림 | O(log N), 빠름 |
| 쓰기 속도 | 빠름 | 인덱스 갱신 비용 추가로 느려짐 |
| 저장 공간 | 그대로 | 인덱스만큼 추가 |
| 적합한 컬럼 | - | WHERE/JOIN에 자주 쓰이고 중복 적은 컬럼 |
