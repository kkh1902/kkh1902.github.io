## TL;DR

트리는 "가계도" 같은 계층 구조 전체를 말하고, BST는 그중 "왼쪽은 작고 오른쪽은 큰" 규칙을
더한 버전, B-Tree는 그 규칙을 메모리가 아니라 디스크(블록 단위 I/O)에 맞게 "한 노드에 여러
값을 담도록" 개량한 버전이다. 셋은 경쟁 관계가 아니라 "쓰이는 환경이 다른" 단계적 발전이다.

## 비유 한 줄

트리 = 회사 조직도(상하관계만 있음, 정렬 규칙 없음). BST = 알파벳 순으로 정리된 이진 분류
서랍(왼쪽 서랍엔 더 작은 것, 오른쪽엔 더 큰 것). B-Tree = 디스크 블록 크기에 맞춰 한 서랍에
여러 칸을 넣은 도서관 서가(한 번 꺼낼 때(디스크 접근 1회) 여러 값을 한꺼번에 봄).

## 개념 표

| 용어 | 비유 | 한줄 설명 |
|---|---|---|
| 트리(Tree) | 회사 조직도 | 노드와 간선으로 이루어진 계층 구조, 순환 없음, 정렬 규칙 없음 |
| 이진트리(Binary Tree) | 한 사람 밑에 부하 2명까지만 | 각 노드가 자식을 최대 2개만 가짐 |
| 이진탐색트리(BST) | 알파벳 순 이진 서랍 | 왼쪽 서브트리는 모두 작은 값, 오른쪽은 모두 큰 값 — 탐색 평균 O(log N) |
| BST의 약점 | 한쪽으로만 쌓인 서랍 | 정렬된 데이터를 순서대로 넣으면 한쪽으로 길게 치우쳐 O(N)까지 느려짐(편향 트리) |
| B-Tree | 칸 여러 개짜리 서가 한 단 | 한 노드가 여러 개의 키를 가질 수 있는 다진(multi-way) 트리 — 디스크 I/O 횟수를 줄이려고 설계됨 |
| B+Tree | 서가 + 마지막 칸끼리 통로 연결 | B-Tree 변형, 실제 데이터는 리프 노드에만 두고 리프끼리 연결 리스트로 이어 범위 검색에 유리(대부분의 DB 인덱스가 이 구조) |

## 구조 다이어그램

```
[이진탐색트리(BST)]                [B-Tree (차수 3 예시)]
        8                             [10 | 20]
       / \                          /     |      \
      3   10                   [5|7]  [12|15]  [25|30]
     / \    \                   (한 노드에 여러 키,
    1   5    14                  자식도 키 개수+1개)

[편향된 BST — 정렬된 데이터를 그대로 삽입한 경우]
1
 \
  2
   \
    3
     \
      4   ← 사실상 연결리스트, 탐색 O(N)
```

## 동작 원리 (왜?)

| 질문 | 답 |
|---|---|
| 왜 BST는 평균 O(log N)인가? | 매번 비교할 때마다 탐색 범위가 절반으로 줄어드는 이진 분기 구조이기 때문(트리가 균형 잡혀 있을 때) |
| 왜 BST가 때로 O(N)까지 느려지나? | 삽입 순서가 이미 정렬돼 있으면(예: 1,2,3,4...) 모든 노드가 한쪽 자식만 갖는 "편향 트리"가 되어 사실상 연결리스트와 같아지기 때문 — 이를 해결하려고 AVL 트리·레드블랙 트리 같은 "스스로 균형을 맞추는 트리"가 나옴 |
| 왜 DB 인덱스는 BST가 아니라 B-Tree/B+Tree를 쓰나? | 디스크 I/O는 메모리 접근보다 수만 배 느리고, 접근 단위가 "블록"이기 때문. BST는 노드마다 1번씩 디스크를 읽어야 해서 트리 높이만큼 디스크 접근이 필요하지만, B-Tree는 한 노드(=한 블록)에 수백 개 키를 담아 트리 높이 자체를 3~4단계로 낮춤 → 같은 데이터량이어도 디스크 접근 횟수가 훨씬 적음 |
| 왜 B+Tree가 B-Tree보다 범위 검색에 유리한가? | B-Tree는 중간 노드에도 데이터가 있어 범위 검색 시 트리를 오르내려야 하지만, B+Tree는 데이터를 리프에만 두고 리프끼리 연결 리스트로 이어둬서 시작점만 찾으면 그 뒤로는 옆으로 쭉 읽기만 하면 됨 |
| 다진 트리(B-Tree)는 왜 디스크 접근을 줄이나? | "트리 높이 = 디스크 접근 횟수"인 구조에서, 노드당 키 개수(차수)를 늘리면 같은 개수의 데이터를 담는 트리의 높이가 로그 밑(base)이 커져서 급격히 낮아지기 때문(예: 100만 건도 높이 3~4면 충분) |

## 예시

```python
# BST 탐색 (편향 위험 있음)
class Node:
    def __init__(self, val):
        self.val = val
        self.left = self.right = None

def insert(root, val):
    if root is None:
        return Node(val)
    if val < root.val:
        root.left = insert(root.left, val)
    else:
        root.right = insert(root.right, val)
    return root

# 1,2,3,4,5를 순서대로 넣으면 오른쪽으로만 길게 치우친 편향 트리가 됨
# → 실무 DB는 이런 위험을 피하려 균형을 자동 유지하는 B+Tree를 인덱스 구조로 채택
```

## 요약 표

| 구분 | 트리 | BST | B-Tree / B+Tree |
|---|---|---|---|
| 자식 개수 | 제한 없음 | 최대 2개 | 여러 개(차수만큼) |
| 정렬 규칙 | 없음 | 왼쪽<부모<오른쪽 | 노드 내 키 정렬 + 서브트리 범위 규칙 |
| 평균 탐색 | 구조에 따라 다름 | O(log N), 편향 시 O(N) | O(log N), 균형 보장 |
| 주 사용처 | 조직도·파일시스템 등 계층 표현 | 메모리 내 탐색 자료구조 | 데이터베이스/파일시스템 인덱스(디스크 기반) |
