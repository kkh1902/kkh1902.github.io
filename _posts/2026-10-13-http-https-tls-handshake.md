## TL;DR

HTTP는 "엽서"고 HTTPS는 "봉투에 넣고 봉인한 편지"다. 내용은 같아도 HTTPS는 중간에
누가 열어봐도 못 읽게(암호화) + 안 바뀌었다는 걸 보장(무결성) + 진짜 그 서버가 맞는지
증명(인증)까지 해준다 — 그 자물쇠를 거는 과정이 TLS 핸드셰이크다.

## 비유 한 줄

HTTP로 쇼핑몰 비밀번호를 보내는 건 엽서에 비밀번호를 적어 우체부 손을 여러 번 거쳐
보내는 것과 같다 — 중간에 누구나 읽을 수 있다. HTTPS는 받는 사람(서버)의 자물쇠(공개키)로
미리 잠근 봉투에 넣어 보내서, 그 자물쇠의 열쇠(개인키)를 가진 서버만 열어볼 수 있다.

## 개념 표

| 용어 | 비유 | 한줄 설명 |
|---|---|---|
| 대칭키 암호화 | 똑같은 열쇠 2개를 미리 나눠 가짐 | 암호화·복호화에 같은 키 사용, 빠르지만 키 전달이 문제 |
| 비대칭키(공개키) 암호화 | 자물쇠(공개)는 누구나, 열쇠(개인)는 나만 | 공개키로 잠그면 그 짝인 개인키로만 열림, 느리지만 키 전달이 안전 |
| 인증서(Certificate) | 신분증 + 공증 도장 | 서버의 공개키 + "진짜 이 도메인 소유자가 맞다"는 CA의 서명 |
| CA(인증기관) | 신분증을 발급하는 관공서 | 인증서에 서명해 신뢰를 보증하는 제3자 |
| 세션 키(Session Key) | 이번 통화에서만 쓰는 임시 암호 | 핸드셰이크로 교환한 대칭키, 실제 데이터는 이걸로 암호화(빠름) |

## 구조 다이어그램

```
[TLS 1.2 핸드셰이크 (단순화)]
Client                                    Server
  |-- ClientHello (지원 암호화 방식 목록) ------->|
  |<-- ServerHello + 인증서(공개키 포함) ---------|
  | (CA 서명 검증 -> 서버가 진짜인지 확인)          |
  |-- 대칭키 재료를 서버 공개키로 암호화해 전송 --->|
  |<-- (양쪽이 같은 세션 키 계산 완료) ------------>|
  |===== 이후 통신은 세션 키(대칭키)로 암호화 =====|
```

## 동작 원리(왜?)

| 질문 | 답 |
|---|---|
| 왜 처음엔 비대칭키, 이후엔 대칭키로 바꾸나? | 비대칭키는 안전하지만 연산이 무거워 느리다 — 처음 "열쇠 교환"만 비대칭키로 안전하게 하고, 실제 대량 데이터 암호화는 빠른 대칭키로 한다(하이브리드 방식) |
| 인증서는 왜 필요한가? | 공개키 자체는 누구나 만들 수 있어서, "이 공개키가 진짜 example.com 서버 것"이라는 걸 제3자(CA)가 보증해야 가짜 서버(중간자 공격)를 걸러낼 수 있다 |
| HTTP/2나 HTTP/3는 뭐가 다른가? | HTTP/2는 하나의 TCP 연결로 여러 요청을 동시에 처리(멀티플렉싱), HTTP/3는 TCP 대신 UDP 기반 QUIC을 써서 연결 수립 지연까지 줄인다 — 둘 다 HTTPS 위에서 동작하는 게 기본 |

## 예시

```
# HTTP (평문)
GET /login?pw=1234 HTTP/1.1   <- 중간에서 그대로 읽힘

# HTTPS (암호화됨, 실제로 전선 위를 흐르는 건 아래처럼 보임)
17 03 03 00 45 a1 3f ... (암호화된 바이트, 핸드셰이크 이후)
```

## 요약 표

| 구분 | HTTP | HTTPS |
|---|---|---|
| 포트 | 80 | 443 |
| 암호화 | 없음(평문) | TLS로 암호화 |
| 서버 신원 확인 | 없음 | 인증서로 확인 |
| 속도 | 핸드셰이크 없이 빠름 | 핸드셰이크 1~2 RTT 추가(TLS 1.3은 1 RTT로 단축) |
| 요즘 기본값 | 거의 안 씀 | 사실상 웹 표준(검색엔진도 HTTPS 우대) |
