## TL;DR

데드락은 "식사하는 철학자" 문제처럼, 네 사람이 젓가락 한 짝씩만 쥐고 서로 상대방 젓가락을
기다리며 영원히 멈춰버리는 상태다. 네 가지 조건(상호배제·점유와 대기·비선점·원형대기)이
동시에 성립해야만 발생하므로, 그중 하나만 깨면 막을 수 있다.

## 비유 한 줄

네 명이 원탁에 앉아 각자 젓가락을 한 짝씩만 쥐고, 양손 젓가락이 다 있어야 먹을 수 있는데
모두가 옆 사람 젓가락을 쥔 채 놓지 않고 기다리기만 하는 상황.

## 개념 표

| 조건 | 비유 | 한줄 설명 |
|---|---|---|
| 상호 배제(Mutual Exclusion) | 젓가락은 한 번에 한 명만 | 자원을 한 번에 하나의 프로세스만 사용 가능 |
| 점유와 대기(Hold and Wait) | 왼쪽 젓가락 쥔 채 오른쪽 기다림 | 자원을 쥔 채로 다른 자원을 추가로 요청 |
| 비선점(No Preemption) | 남의 젓가락을 강제로 뺏을 수 없음 | 프로세스가 스스로 놓기 전까지 자원을 강제로 뺏을 수 없음 |
| 원형 대기(Circular Wait) | A→B→C→A 순으로 서로 기다림 | 프로세스들이 자원 요청 순서상 원을 이룸 |
| 자원 할당 그래프 | 누가 누구 젓가락을 기다리는지 그린 그림 | 그래프에 사이클이 생기면 데드락 발생 가능 신호 |

## 구조 다이어그램

```
[프로세스 A] --쥐고 있음--> [자원 1]
      │                         │
   요청(대기)                요청(대기)
      ▼                         ▼
   [자원 2] <--쥐고 있음-- [프로세스 B]

      A는 자원1을 쥔 채 자원2를 기다리고,
      B는 자원2를 쥔 채 자원1을 기다림 → 원형 대기 발생 → 데드락
```

## 동작 원리 (왜?)

| 질문 | 답 |
|---|---|
| 왜 4가지 조건이 "동시에" 성립해야 하나? | 하나라도 빠지면 순환 대기 자체가 만들어지지 않음 — 예를 들어 자원을 강제로 뺏을 수 있다면(선점 가능) 순환이 끊어짐 |
| 왜 예방(Prevention)은 자원 활용률이 떨어지나? | "필요한 자원을 한 번에 전부 요청"처럼 조건 자체를 없애버리면 안전하지만, 자원을 미리 과도하게 점유하게 돼 낭비가 생김 |
| 왜 회피(Avoidance, Banker's Algorithm)가 현실에서 드문가? | 모든 프로세스가 최대 자원 요구량을 미리 선언해야 하는데, 현실 시스템에서는 그 값을 정확히 알기 어려움 |
| 왜 탐지 후 복구(Detection & Recovery)를 많이 쓰나? | 평소엔 제약 없이 자유롭게 돌리다가, 자원 할당 그래프에서 사이클이 생겼을 때만 프로세스를 골라 강제 종료/롤백하면 되므로 평상시 성능 손해가 적음 |

## 예시

```python
import threading

lock_a = threading.Lock()
lock_b = threading.Lock()

def worker1():
    with lock_a:          # 자원 A를 쥔 채
        with lock_b:      # 자원 B를 요청
            print("worker1 완료")

def worker2():
    with lock_b:          # 자원 B를 쥔 채
        with lock_a:      # 자원 A를 요청 -> 락 획득 순서가 반대라 데드락 위험
            print("worker2 완료")

# 해결책: 모든 스레드가 항상 같은 순서(A -> B)로 락을 획득하게 강제하면
# 원형 대기 조건 자체가 깨져 데드락이 발생하지 않는다.
```

## 요약 표

| 전략 | 방법 | 트레이드오프 |
|---|---|---|
| 예방(Prevention) | 4조건 중 하나를 구조적으로 제거(예: 락 획득 순서 고정) | 자원 활용률 저하 |
| 회피(Avoidance) | Banker's Algorithm으로 안전 상태만 허용 | 최대 요구량 사전 선언 필요, 현실성 낮음 |
| 탐지 후 복구(Detection & Recovery) | 자원 할당 그래프 사이클 탐지 → 프로세스 종료/롤백 | 평소 성능 좋음, 복구 시 비용 발생 |
| 무시(Ostrich Algorithm) | 아무 조치 안 함(대부분의 범용 OS 기본값) | 드물게 발생하면 그때 재부팅 등으로 대응 |
