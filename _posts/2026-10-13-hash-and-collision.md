## TL;DR

해시 테이블은 "사물함 번호표"다. 이름(키)을 해시 함수에 넣으면 사물함 번호(인덱스)가
나오고, 그 번호로 바로 찾아가니 평균 O(1)이다. 문제는 사물함 수는 한정인데 이름은
무한해서 같은 번호가 나오는 경우(충돌)가 생긴다는 것 — 체이닝과 오픈 어드레싱이 그걸
푸는 두 가지 방법이다.

## 비유 한 줄

해시 함수 = 이름을 보고 사물함 번호를 정해주는 규칙. 해시 충돌 = "Lee"와 "Chun"이 같은
규칙을 거쳐 우연히 같은 사물함 번호(5번)를 받는 상황.

## 개념 표

| 용어 | 비유 | 한줄 설명 |
|---|---|---|
| 해시 함수 | 이름→사물함 번호 변환 규칙 | 임의 길이 입력을 고정 길이 값으로 변환, 같은 입력 → 항상 같은 출력 |
| 해시 테이블 | 사물함 전체 | 해시 값을 인덱스로 써서 데이터를 저장하는 배열 구조 |
| 해시 충돌 | 두 사람이 같은 사물함 번호 받음 | 서로 다른 키가 같은 해시 값을 갖는 상황 |
| 체이닝 | 한 사물함에 선반 추가해서 여러 명 수납 | 같은 칸에 연결 리스트를 달아 충돌 데이터를 계속 추가 |
| 오픈 어드레싱 | 내 사물함이 찼으면 옆 빈 칸 쓰기 | 테이블 안의 다른 빈 자리를 찾아 저장(선형/제곱 탐사) |
| load factor | 사물함 꽉 찬 비율 | 키 개수/버킷 수, 0.7~0.8 넘으면 테이블 크기 늘리고 재해싱 |

## 구조 다이어그램

```
[체이닝]                          [오픈 어드레싱]
버킷0: ∅                          버킷0: ∅
버킷1: ∅                          버킷1: ∅
버킷2: "Kim"                      버킷2: "Kim"
버킷3: ∅                          버킷3: ∅
버킷4: ∅                          버킷4: ∅
버킷5: "Lee" → "Chun" (연결리스트)  버킷5: "Lee"
버킷6: ∅                          버킷6: "Chun" ← 5번이 차있어 옆칸(선형 탐사)으로 이동
```

## 동작 원리 (왜?)

| 질문 | 답 |
|---|---|
| 왜 평균 O(1)인가? | 키를 해시 함수에 넣으면 바로 버킷 위치가 나와서, 트리처럼 비교하며 내려갈 필요 없이 한 번에 접근 가능 |
| 왜 충돌이 생기는가? | 해시 값의 범위(예: 버킷 100개)는 유한한데 입력 데이터는 무한히 늘어날 수 있어 비둘기집 원리상 겹침이 불가피함 |
| 체이닝과 오픈 어드레싱의 트레이드오프는? | 체이닝은 저장 개수 제한이 없지만 리스트 노드만큼 메모리를 더 쓰고, 오픈 어드레싱은 추가 메모리가 없지만 테이블이 꽉 차면 빈 자리를 찾는 비용이 커짐 |
| 왜 load factor 관리가 중요한가? | 버킷이 꽉 찰수록 체이닝은 리스트가 길어지고 오픈 어드레싱은 빈 자리 탐색이 길어져 둘 다 O(1)이 무너짐 — 그래서 기준치를 넘으면 테이블을 키우고 재해싱함 |

## 예시

```python
# 파이썬 dict는 내부적으로 해시 테이블(오픈 어드레싱 변형)로 구현됨
cache = {}
cache["Lee"] = "010-1111"
cache["Chun"] = "010-2222"  # 해시 충돌이 나도 파이썬이 내부적으로 처리

print(cache["Lee"])  # O(1) 평균 조회

# 직접 해시 함수를 확인해보기
print(hash("Lee") % 10, hash("Chun") % 10)  # 같은 값이 나오면 충돌 상황
```

## 요약 표

| 항목 | 체이닝 | 오픈 어드레싱 |
|---|---|---|
| 충돌 처리 | 같은 버킷에 연결 리스트 추가 | 다른 빈 버킷을 찾아 저장 |
| 추가 메모리 | 필요(리스트 노드) | 불필요 |
| 저장 한계 | 없음 | 테이블 크기만큼 |
| 대표 사용처 | Java HashMap(일정 길이 넘으면 트리로 전환) | 파이썬 dict |
