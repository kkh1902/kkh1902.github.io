## TL;DR

SQL은 "칸이 정해진 서랍장"이고 NoSQL은 "아무거나 담는 바구니"다. 데이터 구조가 명확하고
관계가 중요하면 SQL, 구조가 자주 바뀌거나 양이 폭증하면 NoSQL — 둘 중 하나가 항상 이기는
게 아니라 데이터 모양과 트래픽 패턴이 정답을 정한다.

## 비유 한 줄

SQL은 옷마다 칸이 정해진 서랍장(열·타입 고정, 규칙 위반하면 안 들어감), NoSQL은 종류
상관없이 던져 넣는 바구니(문서마다 필드가 달라도 됨) — 서랍장은 찾기 쉽지만 칸을 바꾸려면
공사가 필요하고, 바구니는 빠르게 던져 넣을 수 있지만 안을 뒤져야 할 수도 있다.

## 개념 표

| 구분 | SQL (관계형) | NoSQL (비관계형) |
|---|---|---|
| 스키마 | 고정(테이블·열·타입 미리 정의) | 유연(문서/키마다 필드 달라도 됨) |
| 확장 방식 | 수직 확장(서버 사양 업) 위주 | 수평 확장(서버 대수 늘리기) 쉬움 |
| 일관성 | ACID 강한 일관성 | 대부분 최종 일관성(eventual consistency) |
| 관계 표현 | JOIN으로 테이블 간 관계 표현 | 보통 비정규화(중복 저장)로 JOIN 회피 |
| 대표 제품 | MySQL, PostgreSQL, Oracle | MongoDB(문서), Redis(키-값), Cassandra(컬럼) |
| 잘 맞는 경우 | 결제·재고처럼 정합성이 생명인 데이터 | 로그·세션·실시간 피드처럼 양 많고 구조 유동적 |

## 구조 다이어그램

```
[SQL]                         [NoSQL - 문서형]
users 테이블                   users 컬렉션
+----+-------+-------+        { id:1, name:"A", hobby:["게임"] }
| id | name  | email |        { id:2, name:"B" }  <- 필드 달라도 OK
+----+-------+-------+
   |  (JOIN)
orders 테이블
+----+--------+
| id | userid |
+----+--------+
```

## 동작 원리(왜?)

| 질문 | 답 |
|---|---|
| 왜 SQL은 수평 확장이 어려운가? | 여러 서버에 테이블을 나누면 JOIN·트랜잭션이 서버 경계를 넘어야 해서 비싸진다(분산 트랜잭션 문제) |
| 왜 NoSQL은 최종 일관성으로 타협하나? | CAP 정리상 분산 환경에서 일관성(C)·가용성(A)·분단 내성(P)을 동시에 다 못 잡는다 — 대부분 NoSQL은 P+A를 택하고 C를 느슨하게 둔다 |
| 왜 NoSQL은 비정규화를 하나? | JOIN 비용이 커서, 자주 같이 조회하는 데이터는 애초에 한 문서에 중복 저장해 조회를 1회로 끝낸다 |

## 예시

```sql
-- SQL: 정규화된 테이블, JOIN으로 관계 조회
SELECT u.name, o.product
FROM users u JOIN orders o ON u.id = o.userid
WHERE u.id = 1;
```

```json
// NoSQL(문서형): 비정규화, 한 문서 안에 주문까지 포함
{
  "id": 1,
  "name": "A",
  "orders": [{"product": "노트북"}, {"product": "마우스"}]
}
```

## 요약 표

| 상황 | 선택 |
|---|---|
| 결제·재고·회원처럼 정합성 필수 | SQL |
| 트래픽이 예측 불가하게 늘어나는 서비스 | NoSQL (수평 확장) |
| 데이터 구조가 자주 바뀌는 초기 서비스 | NoSQL |
| 복잡한 다중 테이블 관계 조회가 많음 | SQL |
| 둘 다 필요할 때 | 폴리글랏 퍼시스턴스(용도별로 혼용) — 예: 회원 DB는 PostgreSQL, 세션/캐시는 Redis |
