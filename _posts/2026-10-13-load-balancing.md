## TL;DR

로드밸런서는 "여러 창구 앞에 선 손님을 비는 창구로 안내하는 안내원"이다. 서버 한 대가
감당 못 할 트래픽을 여러 대로 나눠 받게 해서, 속도도 올리고 한 대가 죽어도 서비스가
안 멈추게 해준다.

## 비유 한 줄

은행 창구가 하나면 아무리 빨라도 줄이 길어지고, 그 창구 직원이 자리를 비우면 업무가
완전히 멈춘다 — 로드밸런서는 입구에 서서 "3번 창구로 가세요"라고 안내하는 직원이고,
창구 하나가 비면 그쪽으로는 안내를 멈춘다(헬스체크).

## 개념 표

| 용어 | 비유 | 한줄 설명 |
|---|---|---|
| 라운드 로빈(Round Robin) | 순서대로 돌아가며 배정 | 요청을 서버에 순차적으로 균등 분배 |
| 가중 라운드 로빈 | 일 잘하는 직원에게 더 많이 배정 | 서버 성능에 따라 가중치를 둬 분배 비율 차등 |
| 최소 연결(Least Connections) | 지금 제일 한가한 창구로 보냄 | 현재 처리 중인 연결 수가 가장 적은 서버로 전달 |
| 헬스체크(Health Check) | 창구 직원이 자리에 있는지 주기적으로 확인 | 서버 생존 여부를 주기적으로 확인해 죽은 서버는 제외 |
| L4 로드밸런싱 | 주소만 보고 안내(내용은 안 봄) | 전송 계층(IP·포트) 기준으로 분배, 빠름 |
| L7 로드밸런싱 | 용건까지 듣고 담당 창구로 안내 | 응용 계층(URL·헤더·쿠키) 기준으로 분배, 세밀하지만 느림 |

## 구조 다이어그램

```
                [로드밸런서]
                 /    |    \
          (헬스체크로 살아있는 서버만 선택)
              /       |        \
       [서버 A]   [서버 B]   [서버 C: 응답 없음 -> 제외]
       (정상)      (정상)

클라이언트 요청 -> 로드밸런서 -> 서버 A 또는 B로 분배 (C는 자동 제외)
```

## 동작 원리(왜?)

| 질문 | 답 |
|---|---|
| 왜 단순 라운드 로빈만 쓰지 않나? | 서버 성능이 다르거나 요청마다 처리 시간이 다르면, 순서대로만 분배해도 특정 서버에 느린 요청이 몰려 과부하가 생길 수 있다 — 그래서 최소 연결·가중치 방식을 섞는다 |
| L4 vs L7, 뭘 선택하나? | 단순 트래픽 분산(빠른 속도)이 목적이면 L4, URL 경로별로 다른 서버로 보내거나(예: /api → API 서버) 쿠키 기반 세션 유지가 필요하면 L7 |
| 세션(로그인 상태)은 어떻게 유지되나? | 서버마다 세션을 따로 저장하면 같은 사용자가 매번 다른 서버로 가면 로그인이 풀린다 — "고정 세션(Sticky Session)"으로 같은 사용자를 같은 서버로 보내거나, Redis 등 외부 세션 저장소로 서버 간 세션을 공유해 해결한다 |

## 예시

```nginx
# nginx를 L7 로드밸런서로 쓰는 간단 예시
upstream backend {
    least_conn;              # 최소 연결 방식
    server 10.0.0.1:8080;
    server 10.0.0.2:8080;
}
server {
    location / {
        proxy_pass http://backend;
    }
}
```

## 요약 표

| 목적 | 로드밸런싱이 해결하는 문제 |
|---|---|
| 성능 | 트래픽을 여러 서버로 나눠 응답 속도 개선 |
| 가용성 | 서버 한 대가 죽어도 헬스체크로 제외해 서비스 지속 |
| 확장성 | 트래픽 증가 시 서버만 추가하면 수평 확장 가능 |
| 유연성 | L7 방식으로 URL·쿠키 기반 세밀한 라우팅 가능 |
