## TL;DR

이분 탐색은 "정렬된 사전에서 단어 찾기"다. 처음부터 한 장씩 넘기지 않고 가운데를 펼쳐
찾는 단어보다 앞인지 뒤인지 보고 범위를 절반씩 줄여나간다. 조건은 딱 하나 —
**데이터가 정렬돼 있어야 한다**. 시간복잡도는 O(log n)으로, 100만 개 중에서도 약 20번
비교하면 끝난다.

## 비유 한 줄

전화번호부에서 "박○○"을 찾을 때 1페이지부터 넘기지 않고 중간을 펼쳐 "ㅅ"이 나오면
앞쪽 절반으로, "ㄱ"이 나오면 뒤쪽 절반으로 범위를 좁혀가는 것.

## 개념 표

| 용어 | 비유 | 한줄 설명 |
|---|---|---|
| left / right | 뒤질 범위의 양 끝 페이지 | 탐색 대상이 될 수 있는 구간의 경계 인덱스 |
| mid | 펼친 중간 페이지 | `(left + right) // 2` — 이 값과 목표를 비교해 다음 범위 결정 |
| 선형 탐색(Linear Search) | 처음부터 한 장씩 넘기기 | 정렬 여부와 무관, O(n) |
| 로그 시간(O(log n)) | 매번 절반씩 버리기 | 범위가 매번 반으로 줄어 n번이 아니라 log₂n번 만에 끝남 |

## 구조 다이어그램

```
배열(정렬됨): [1, 3, 5, 7, 9, 11, 13, 15]   목표: 11
인덱스:        0  1  2  3  4   5   6   7

1단계: left=0, right=7, mid=3 → arr[3]=7 < 11 → 왼쪽 버림
       [________________|  7   9  11  13  15]
                          left=4         right=7

2단계: left=4, right=7, mid=5 → arr[5]=11 == 11 → 찾음!

비교 횟수: 2번 (선형 탐색이면 최악 6번 필요했음)
```

## 동작 원리(왜?)

| 질문 | 답 |
|---|---|
| 왜 꼭 정렬이 전제조건인가? | mid 값과 비교해 "한쪽 절반을 통째로 버리는" 판단이 가능한 건 그 절반이 전부 더 크거나 작다고 보장되기 때문 — 정렬이 안 돼 있으면 이 보장이 깨짐 |
| 왜 O(log n)인가? | 매 단계마다 탐색 범위가 절반으로 줄어듦. n을 절반씩 k번 나눠 1이 되는 k가 log₂n이므로, 비교 횟수도 log₂n에 비례 |
| `(left + right) // 2`는 왜 위험할 수 있나? | left+right가 int 최댓값을 넘으면 오버플로 발생(언어에 따라). `left + (right - left) // 2`가 더 안전 |
| 실무에서 어디 쓰이나? | DB 인덱스 탐색(B-Tree 내부도 결국 분기 탐색), 정렬된 로그에서 특정 시각 찾기, `bisect` 모듈로 "값이 들어갈 위치" 찾기(결정 문제를 이분 탐색으로 푸는 파라메트릭 서치) |

## 예시

```python
def binary_search(arr, target):
    left, right = 0, len(arr) - 1
    while left <= right:
        mid = left + (right - left) // 2
        if arr[mid] == target:
            return mid
        elif arr[mid] < target:
            left = mid + 1
        else:
            right = mid - 1
    return -1  # 못 찾음

arr = [1, 3, 5, 7, 9, 11, 13, 15]
print(binary_search(arr, 11))  # 5
print(binary_search(arr, 4))   # -1
```

## 요약 표

| 비교 | 선형 탐색 | 이분 탐색 |
|---|---|---|
| 전제조건 | 없음 | 정렬 필수 |
| 시간복잡도 | O(n) | O(log n) |
| 100만 개 기준 최악 비교 횟수 | 1,000,000 | 약 20 |
| 구현 난이도 | 쉬움 | mid 계산·경계(`<=`/`<`) 실수 주의 |
