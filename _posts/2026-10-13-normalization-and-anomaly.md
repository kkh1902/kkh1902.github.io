## TL;DR

정규화는 "같은 정보를 두 번 적지 않도록 테이블을 쪼개는 작업"이다. 안 쪼개면 데이터를
넣고(삽입)·지우고(삭제)·고칠(갱신) 때 이상한 일(이상현상)이 생긴다 — 정규화는 그걸 막는
예방접종이다.

## 비유 한 줄

학생 명부에 "학생-수강과목-교수님 연구실" 정보를 한 표에 다 적으면, 교수님이 연구실을
옮길 때마다 그 교수가 가르치는 수십 개 수강 행을 전부 찾아 고쳐야 한다 — 하나라도 빠뜨리면
같은 교수인데 연구실이 두 가지로 적힌 모순이 생긴다. 정규화는 "교수 정보는 교수 표에
한 번만" 적도록 쪼개서 이 문제를 없앤다.

## 개념 표

| 용어 | 비유 | 한줄 설명 |
|---|---|---|
| 삽입 이상(Insertion Anomaly) | 신입생이 아직 수강신청 안 하면 등록 자체가 안 됨 | 관련 없는 정보가 없으면 필요한 정보도 못 넣는 문제 |
| 삭제 이상(Deletion Anomaly) | 마지막 수강생이 자퇴하면 그 과목 정보까지 같이 사라짐 | 한 행을 지웠는데 의도치 않은 다른 정보까지 같이 삭제됨 |
| 갱신 이상(Update Anomaly) | 교수 연구실 변경 시 수십 행을 다 고쳐야 함 | 중복 저장된 값 중 일부만 고쳐 데이터가 불일치해짐 |
| 제1정규형(1NF) | 한 칸에 하나의 값만 | 반복 그룹/다중값 속성 제거(원자값) |
| 제2정규형(2NF) | 부분적으로만 관련된 정보 분리 | 기본키 일부에만 종속되는 속성 분리(부분 함수 종속 제거) |
| 제3정규형(3NF) | 간접적으로만 관련된 정보 분리 | 기본키가 아닌 속성에 종속되는 속성 분리(이행적 종속 제거) |

## 구조 다이어그램

```
[정규화 전: 한 테이블에 다 섞임]
수강(학번, 과목, 교수, 교수연구실)
 1   DB    김교수  301호     <- 교수가 여러 과목 가르치면 "301호"가 여러 행에 중복

        정규화
          |
          v
[정규화 후: 책임 분리]
수강(학번, 과목, 교수)        교수(교수, 연구실)
 1    DB    김교수            김교수  301호   <- 연구실은 여기 한 번만
 2    OS    김교수
```

## 동작 원리(왜?)

| 질문 | 답 |
|---|---|
| 정규화를 안 하면 왜 위험한가? | 같은 사실(교수 연구실)이 여러 곳에 중복 저장되면, 갱신 시 일부만 바뀌어 "같은 교수인데 연구실이 두 개"인 모순 상태가 생길 수 있다 |
| 정규화를 하면 뭘 잃나? | 조회할 때 여러 테이블을 JOIN해야 해서 쓰기는 안전해지지만 읽기는 느려질 수 있다 — 그래서 읽기가 압도적으로 많은 시스템은 일부러 반정규화(denormalization)한다 |
| 어디까지 쪼개야 하나? | 실무에선 보통 3NF까지. BCNF·4NF 이상은 이론적으로만 다루는 경우가 많다 |

## 예시

```sql
-- 정규화 전: 교수연구실이 과목마다 중복
수강(학번, 과목, 교수, 교수연구실)

-- 정규화 후: 교수 테이블 분리, FK로 연결
CREATE TABLE 교수 (교수명 VARCHAR PRIMARY KEY, 연구실 VARCHAR);
CREATE TABLE 수강 (학번 INT, 과목 VARCHAR, 교수명 VARCHAR REFERENCES 교수(교수명));
```

## 요약 표

| 이상현상 | 원인 | 정규화로 해결 |
|---|---|---|
| 삽입 이상 | 무관한 데이터가 묶여 있음 | 관련 없는 속성을 별도 테이블로 |
| 삭제 이상 | 한 정보가 다른 정보에 얹혀 있음 | 독립적인 개체는 독립 테이블로 |
| 갱신 이상 | 같은 값이 여러 행에 중복 | 중복 제거(한 곳에만 저장) |
| 트레이드오프 | 쓰기 안전 ↔ 읽기 성능 | 조회 많으면 반정규화도 선택지 |
