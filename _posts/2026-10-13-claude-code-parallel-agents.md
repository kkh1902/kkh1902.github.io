## 왜 구분해야 하나

"에이전트를 여러 개 돌린다"는 말이 가리키는 방식이 실제로는 네 가지나 된다.
이걸 구분하지 않고 아무거나 쓰면 두 가지 문제가 생긴다 — 간단한 일에
무거운 방식을 써서 토큰을 낭비하거나, 반대로 진짜 병렬이 필요한 일을
순차로 처리해서 느려진다. 선택 기준은 결국 하나로 좁혀진다: **누가
조율하는가, 그리고 작업자끼리 소통이 필요한가.**

## 1) 서브에이전트 — 같은 세션 안에서 위임

메인 대화가 검색 결과나 로그로 넘칠 것 같을 때, 부작업을 서브에이전트에게
맡기고 요약만 받는다. 조율자는 메인 세션 자신이다. 가장 가볍고 가장 자주
쓰게 되는 방식 — "이 부분은 확인만 해서 알려줘" 같은 일에 적합하다.

## 2) 에이전트 뷰 — 백그라운드 세션을 화면에서 관리

여러 독립적인 작업을 한꺼번에 던져두고, 필요할 때만 들여다보고 싶을 때
쓴다. 서로 다른 작업들이 완전히 독립적이라 서로의 결과를 알 필요가 없을
때 적합하다. "이것도 해놓고, 저것도 해놓고" 식으로 퇴근 전에 여러 개
걸어두는 용도로 써봤는데, 작업 사이에 의존성이 없을 때만 깔끔하게 맞는다.

## 3) 에이전트 팀 — 공유 작업 목록으로 조율

여러 세션이 하나의 작업 목록과 메시징으로 서로 소통하며 움직인다. 리더가
전체를 관리한다. 서브에이전트나 에이전트 뷰와 다른 점은 "작업자들끼리
서로의 진행 상황을 알아야 하는가"다 — 한쪽이 끝나야 다른 쪽이 시작할 수
있는 식으로 의존성이 있으면 이 방식이 맞다.

## 4) 동적 워크플로우 — 스크립트로 대규모 조율

많은 서브에이전트를 스크립트가 직접 실행하고 결과를 교차 검증한다.
코드베이스 전체 감사나 대규모 마이그레이션처럼, 사람이 한 번에 다
조율하기엔 너무 큰 작업에 쓴다. 스크립트로 짜두면 같은 작업을 나중에
그대로 재실행할 수 있다는 것도 장점이다.

## 선택할 때 보는 것

1. **동일 파일을 여러 작업자가 건드리는가** — 그렇다면 worktree로 격리해야
   충돌을 피한다.
2. **작업자끼리 서로의 결과를 알아야 하는가** — 알아야 하면 팀, 몰라도
   되면 서브에이전트나 에이전트 뷰.
3. **조율자가 사람(대화)인가, 스크립트인가** — 재사용 가능한 절차라면
   스크립트(동적 워크플로우)로 뽑아두는 게 낫다.

여러 세션을 동시에 돌리면 토큰 사용량이 그만큼 늘어난다는 점도 잊지 않는
게 좋다. 병렬화는 속도를 위한 선택이지 공짜가 아니다.
